# SteamSPA 本地维护笔记

> 本文档仅作为本地维护记录，`docs/` 不上传 GitHub。  
> 对外公开仓库保持极简：`.gitignore`、`README.md`、`uninstall.ps1`。

## 当前项目定位

SteamSPA 只做一件事：

1. 识别 Steam 假入库 / 解锁脚本留下的残留。
2. 展示扫描结果。
3. 用户确认后清理。

对外只维护一个脚本：

```text
uninstall.ps1
```

不再维护：

- `targets.json`
- `targets.schema.json`
- 远程 bootstrap 脚本
- 快捷方式生成器
- 对外 docs / dev / scripts 目录

## 对外使用方式

推荐：

```powershell
irm https://raw.githubusercontent.com/ZERONE2077/SteamSPA/refs/heads/main/uninstall.ps1 | iex
```

CDN：

```powershell
irm https://cdn.jsdelivr.net/gh/ZERONE2077/SteamSPA@main/uninstall.ps1 | iex
```

流程固定为：

```text
扫描 → 显示残留 → 输入 Y 才清理 → 其他输入取消
```

## 当前脚本结构

`uninstall.ps1` 是自包含脚本：

- 规则内置在 `$EmbeddedTargetsJsonBase64`
- 运行时按 UTF-8 解码为 JSON
- 源码保持 ASCII / 无 BOM，避免 `irm | iex` 和 Windows PowerShell 5.1 编码问题
- 中文提示通过 Base64 解码输出
- 报告写入 `temp/logs/`
- 文件备份写入 `temp/backups/`

保留的可选参数：

- `-Risk low,medium,high`
- `-Only <规则ID>`
- `-NoBackup`
- `-NoPause`

普通用户不需要参数。默认会展示 low / medium / high 全部风险项，但仍需确认后才清理。

## 已归纳的假入库 / 解锁类型

### 1. PowerShell 一行命令 / irm 入口

典型形式：

```powershell
irm xxx | iex
iwr xxx -OutFile get.ps1; powershell -File get.ps1
```

常见残留：

- `%USERPROFILE%\get.ps1`
- `%TEMP%\*.ps1`
- `${ScriptRoot}\a.ps1`
- Steam 根目录 DLL
- `HKCU:\Software\Valve\Steamtools`
- Defender 排除项

已见来源：

- `steam-run.com`
- `steam.run`
- `cdks.run`
- `cdk.ruku.run`
- `steam.work` / `steam.icu`

### 2. DLL 代理 / Hook 类

常见文件：

- `${SteamPath}\dwmapi.dll`
- `${SteamPath}\xinput1_4.dll`
- `${SteamPath}\hid.dll`
- `${SteamPath}\zlib1.dll`
- `${SteamPath}\version.dll`

策略：

- 明确工具落地文件可以清理。
- 可能包含用户自定义内容的目录标记为 `medium`，确认后清理。
- 不删除整个 Steam 目录。

### 3. Steamtools / 注册表类

常见注册表：

```text
HKCU:\Software\Valve\Steamtools
```

常见值：

- `packageinfo`
- `steamclient`
- `s`
- `c`
- `iscdkey`
- `ActivateUnlockMode`
- `AlwaysStayUnlocked`
- `notUnlockDepot`

策略：

- 精确匹配工具注册表项。
- 不泛删 Steam 正常注册表。

### 4. 配置 / Manifest / Depot 注入类

常见位置：

- `${SteamPath}\config\appdata.vdf`
- `${SteamPath}\appcache\appdata.vdf`
- `${SteamPath}\appcache\packageinfo.vdf`
- `${SteamPath}\package\beta`
- `%LOCALAPPDATA%\Steam\localData.vdf`

策略：

- 明确由假入库脚本生成的文件可以加入规则。
- `appmanifest_*.acf`、`depotcache`、Ticket 类内容不泛删，必须有明确 AppID / 来源证据。

### 5. 安全策略 / Defender 绕过类

常见行为：

- 添加 Defender 排除路径：`${SteamPath}`、`%APPDATA%\Stool`
- 添加排除扩展名：`exe`、`dll`、`.exe`、`.dll`
- 修改 SmartScreen
- 修改 CI Policy
- 暂停 Windows Update

策略：

- 统一标记为 `high`
- 必须清楚展示给用户
- 用户确认后才清理

### 6. GUI / 安装包类

已见例子：

- SteamKing

常见残留：

- 安装目录
- `%LOCALAPPDATA%` 应用目录
- 卸载注册表
- 常驻进程
- 启动项 / 服务 / 计划任务

策略：

- 程序文件和本体目录可作为 `medium`。
- 系统级服务、任务、策略按 `medium/high` 处理。

## 新增识别项维护流程

新增一个软件 / 脚本时，按下面流程处理：

1. 保存原始样本到本地 `scripts/<来源>/`。
   - 抓样本时必须带 PowerShell UA：`Mozilla/5.0 (Windows NT 10.0; Microsoft Windows 10.0.19045; zh-CN) WindowsPowerShell/5.1.19041.4046`。
   - 很多站点按 UA 分流：浏览器 UA 给落地页 HTML，PowerShell UA 才给真脚本。只带浏览器 UA 会误判成「站点无关」。
2. 只做静态分析，不直接执行陌生脚本。
3. 总结它写入 / 删除 / 修改的内容：
   - 文件
   - 注册表
   - Defender 排除项
   - SmartScreen / CI Policy
   - 计划任务 / 服务 / 启动项
   - 进程
   - Steam 配置 / Manifest / Ticket
4. 判断风险等级：
   - `low`：明确工具残留，误删风险低
   - `medium`：可能涉及用户配置或正常软件目录
   - `high`：系统安全策略、Defender、SmartScreen、CI Policy、Ticket / AppID 类
5. 把确认后的规则维护进 `uninstall.ps1` 内置规则。
6. 本地测试：
   - 能解析脚本
   - 能扫描
   - 取消清理不会删除
   - 输入 `Y` 时清理逻辑符合预期
7. 提交推送。

## 2026-06-25：禁用 `%LOCALAPPDATA%\Steam` 默认清理

实测清理 `%LOCALAPPDATA%\steam` 后，Steam 会要求重新登录，并可能在扫码登录后卡启动加载界面。

原因：Windows 路径大小写不敏感，`%LOCALAPPDATA%\steam` 与 `%LOCALAPPDATA%\Steam` 实际是同一目录，Steam 客户端会在该目录保存 web/cache/session/userdata/local.vdf 等运行数据。

处理：

- 将规则 `localappdata-steam` 改为 `enabled: false`。
- 不再默认删除 `%LOCALAPPDATA%\Steam`，避免误伤 Steam 正常缓存和登录状态。
- 若个别假入库脚本确实写入该目录，后续应改为只清理明确文件名，而不是删除整个目录。

## 2026-06-25：`appcache\packageinfo.vdf` 清理后的短暂变慢

`Steam\appcache\packageinfo.vdf` 仍保留在默认清理范围内，因为部分假入库/解锁链路会借助 Steam 包/Depot 元数据缓存制造异常状态。

注意：删除该文件后，Steam 下次启动会重新拉取/生成包信息和库元数据；如果同时在下载、卸载或更新游戏，设置页、库页面、下载页可能短暂变慢。实测等待几分钟或重启 Steam 后通常会恢复。

对外注意事项也需要说明：清理后 Steam 第一次打开可能明显变慢，建议用户提前开启 Steam 加速器，避免首次重建缓存时因为网络问题卡在加载或设置页响应慢。

该规则不同于 `%LOCALAPPDATA%\Steam`：前者是可重建的 Steam appcache 单文件，后者包含 WebHelper 缓存、会话和本地状态，不应整目录默认删除。

### 家族指纹：固定样板头（不要照抄）

该家族所有脚本开头都是同一套 4 行样板（`scripts/steam-run.com/` 下 5 个样本、`47.100.121.251.ps1` 等一字不差）：

变体 `scripts/cdk.ruku.run/a.ps1` 把两行 encoding **注释掉**、只留 `$ErrorActionPreference`，说明这段是复制粘贴，作者并未按需裁剪。

| 行 | 本工具 | 原因 |
|---|---|---|

产物：


生成方式（沙箱内 `New-Object -ComObject WScript.Shell` 被安全中心拦截，不能用 COM）：

- 克隆现有 `.lnk` 二进制，只**原位替换 ARGS 段**（2 字节字符数 + UTF-16LE 字符串），其余段（NAME / WORKING_DIR / ICON / ExtraData）与 `RunAsUser`（LinkFlags `0x2000`）原样保留。字符串段顺序遍历、无偏移指针，直接拼接字节即安全。
- 新 ARGS 的 `-EncodedCommand` 仍是 Base64/UTF-16LE，中文只出现在 cmd `title` 和 PowerShell 输出里。
- 校验两步：把 `-EncodedCommand` 解回文本与 payload 源文件逐字符比对；再把 payload 里的 `iex $spaText` 换成报告语句实跑一遍，确认命中第 1 源。

两个注意点：

- URL 仍带 `[guid]::NewGuid()` 防缓存，代价是每次都**缓存未命中**（镜像回源 jsDelivr）。想完全吃 CDN 缓存就去掉这段，但 `@main` 分支最长会陈旧 12 小时。
- 2026-09-11 时本地 HEAD 领先 `origin/main` 2 个提交（`a05db50`、`831fc52`），CDN 上仍是旧版：远端 80637 字节 / 本地 85860 字节。**推送后镜像才更新**。

## 2026-09-12：jsDelivr 源导致中文乱码（客户实机复现）

**结论**：`irm` 拉 jsDelivr 系的脚本会中文乱码，必须按字节取回后自己按 UTF-8 解。09-11 那版 JSD 快捷方式（`irm ($base + 'uninstall.ps1?...')`）是错的，已修正。

**现象**：2026-09-11 23:12 客户实机（Windows 11 25H2 / Build 26200.9445，`C:\Users\zhanc`）跑完后，界面和桌面 TXT 报告里中文全是 `æ«æ`、`âââ`、`ð¥¸`，但流程本身跑完了（发现 14 / 删除 10 / 失败 0）。

**判定**：`æ` / `â` / `ð` 这族字符 = UTF-8 字节被按 ISO-8859-1（≈CP1252）解了一遍。UTF-8 的「扫」`E6 89 AB` → `æ‰«`。

**根因**：jsDelivr 全系（含国内镜像）返回 `Content-Type: application/octet-stream`，Windows PowerShell 5.1 的 `irm`/`iwr` 对**不带 charset** 的响应默认按 ISO-8859-1 解码。`raw.githubusercontent.com` 返回 `text/plain; charset=utf-8`，所以这个坑一直没暴露。

实测（本机 5.1.26100.9352 / 7.6.6）：

| 源 | Content-Type | PS 5.1 `irm` | PS 7 `irm` |
|---|---|---|---|
| `cdn.jsdelivr.net` | `application/octet-stream` | ❌ 乱码（80637 字符 = 逐字节） | ✅ |
| `fastly.jsdelivr.net` / `gcore.jsdelivr.net` | 同上 | ❌ | ✅ |
| `jsd.onmicrosoft.cn` | `application/octet-stream` | ❌ | ✅ |
| `cdn.jsdmirror.com` | `application/octet-stream` | ❌ | ✅ |
| `raw.githubusercontent.com` | `text/plain; charset=utf-8` | ✅ | ✅ |

**复测要求**：pwsh 7 默认 UTF-8，**用 pwsh 7 根本测不出来**，必须 `& powershell.exe -NoProfile -ExecutionPolicy Bypass -Command …` 才算数。

**修正写法**：

```powershell
$spaRaw  = Invoke-WebRequest -Uri $spaUrl -UseBasicParsing -TimeoutSec 30
$spaText = [System.Text.Encoding]::UTF8.GetString($spaRaw.RawContentStream.ToArray()).TrimStart([char]0xFEFF)
```

| 等价写法 | 5.1 | 代价 |
|---|---|---|
| `iwr -OutFile f` + `Get-Content f -Raw -Encoding UTF8` | ✅ | 落盘 |
| `(New-Object Net.WebClient).Encoding = [Text.Encoding]::UTF8` + `DownloadString` | ✅ | 类型已过时 |
| `New-Object System.Net.Http.HttpClient` | ❌ 找不到类型 | 5.1 要先 Add-Type 加载程序集 |
| `[Text.Encoding]::UTF8.GetString($r.Content)` | ❌ | `$r.Content` 已经被错误解码过（octet-stream 时它是 **byte[]**） |

**顺带修掉的功能问题**：脚本里唯一带中文的“数据”是规则里的

```json
"path":  "${SteamPath}\\ANNO117 - 副本.zip"
```

乱码后不再等于真实文件名 → 这条检测失效。其余规则路径全是 ASCII。所以乱码不只是显示问题。

**其它**：
- payload 加了 `$spaText.Length -gt 1000 -and $spaText.Contains('SteamSPA')` 校验，防镜像返回 200 的 HTML 错误页被直接喂进 `iex`。
- `README.md` 的 jsDelivr 段落改成字节级 UTF-8 写法——原来那条 `irm … | iex` 对 5.1 用户就是乱码，客户很可能就是从 README 复制的。
- 两个 JSD `.lnk` 重新生成并校验：`-EncodedCommand` 解回后与 payload 逐字符一致；在 5.1 和 7 下实跑下载逻辑，结果 `cjk-scan=True cjk-path=True`。
